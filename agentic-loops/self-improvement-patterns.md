# External feedback powers every agent self-improvement loop

Agent self-improvement looks like a crowded field, but every working loop has the same five stages: **observe → propose → evaluate → human gate → promote**. What varies is the timescale it runs on (within a turn, within a session, at session end, on a periodic batch, or continuously in production) and the thing it changes (context, memory, tools and skills, harness config and hooks, evals, or weights). The loops that work today in Claude Code, Codex CLI, Cursor, Gemini CLI and Aider share one trait: they are **anchored in a signal from outside the model**. Within a turn that signal is tests, linters and fresh-context reviewers. Within a session it is completion gates enforced by the harness. At session end it is user corrections and transcript statistics, which get turned into edits to CLAUDE.md, skills and settings. Weekly and monthly, it is transcript mining plus eval suites. The research is lopsided on this point. Intrinsic self-critique often makes reasoning *worse* ([Huang et al.](https://arxiv.org/abs/2310.01798)). Skills that agents write cold give **−1.3pp against +16.2pp for curated skills** ([SkillsBench](https://arxiv.org/abs/2602.12670)). Test-gated reflection, lint-guarded edits and benchmark-validated self-modification all produce real gains. The research systems contribute concrete mechanics: Reflexion, ExpeL, ACE, Voyager, DSPy/GEPA, ADAS, DGM, HGM, SICA and AlphaEvolve between them supply delta updates instead of rewrites, verification before storage, archives of variants, and evaluators the agent cannot see. Claude Code now ships many of these loops as first-party features: auto memory, `/insights`, `/fewer-permission-prompts`, `/doctor prompt-audit`, `/goal`, `/loop`, cloud scheduled tasks and the skill-creator eval loop. The main risk is that **persistence amplifies every mistake**. A bad learned rule loads into every future session, and any loop with a gameable metric invites reward hacking or poisoning. For one person, the practical sequence is: verifier hooks and a reviewer subagent first, then a reflection at the end of each session that proposes diffs, a weekly audit pass, a monthly prune, and evals before any optimizer. DGM-style self-modification and weight updates belong in offline R&D.

## Every loop runs observe, propose, evaluate, gate, promote

Loops that look unrelated share a skeleton. The **observe** stage collects evidence: a failing test, a user correction, a transcript, a cluster of production traces. The **propose** stage drafts a change: a code fix, a CLAUDE.md line, a SKILL.md, an allowlist entry, a new agent variant. The **evaluate** stage checks the proposal against something the proposer does not control. The **gate** stage decides whether it ships, usually with a human approving a diff. The **promote** stage makes the change durable: the turn ends, the rule is committed, the skill is packaged as a plugin, or the agent variant enters an archive. The research systems implement the same stages with different machinery. ACE splits the work into a Generator that produces trajectories, a Reflector that extracts lessons, and a Curator that merges **delta updates** deterministically with de-duplication ([ACE repo](https://github.com/ace-agent/ace)). DGM samples parents from an archive, lets each one edit its own repository, and admits children only after empirical benchmark validation ([DGM](https://arxiv.org/abs/2505.22954)) *(not re-verified)*. Community tools such as claude-reflect queue detected corrections and require a y/n approval for each item before anything touches CLAUDE.md ([claude-reflect](https://skills.sh/bayramannakov/claude-reflect/claude-reflect)).

| Stage | Within-session | End-of-session | Periodic | Research analogue |
|---|---|---|---|---|
| Observe | Test, lint and tool output | Transcript, corrections, review comments | Many transcripts, traces, permission logs | Trajectories (ACE Generator, Voyager) |
| Propose | Code fix | CLAUDE.md diff, SKILL.md draft | Allowlist, rule, hook, eval case, prompt variant | ACE Reflector, DGM child |
| Evaluate | Rerun the check | Seen ≥2 times? skill-creator A/B vs no skill | Held-out evals, regression suite | Benchmark (hidden from agent) |
| Gate | Stop-hook decision | Human y/n or PR review | PR review, canary | Archive admission |
| Promote | Turn ends | Commit to `.claude/` or CLAUDE.md | Plugin, managed settings, new default | Archive, playbook bullet |

Two further structures recur. The first is a **promotion ladder** for rules. Practitioners move a lesson from advisory to enforced: CLAUDE.md, then a path-scoped file in `.claude/rules/`, then a skill, then a hook. They promote only when the softer mechanism has demonstrably failed ([Proxify patterns](https://agentic.proxify.io/patterns/system-evolution)). The reason is that CLAUDE.md is "context, not enforced configuration", and anything that must happen belongs in a hook or a `permissions.deny` rule ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). One community README claims skills trigger only "roughly half to four-fifths of the time" while hooks always fire, but it gives no methodology *(secondary)* ([dev.to](https://dev.to/axitslab/our-claude-code-setup-30-skills-mcps-and-self-learning-hooks-5gje)). The second is a **memory hierarchy**. Anthropic's November 2026 memory post orders it from bottom to top as transcripts, then agent-written notes, then memory representations such as linked wikis, then injected context. Injected context loads every session and should be kept smallest. Consolidation promotes high-value notes upward and "mov[es] some details down the hierarchy and leav[es] links behind" ([Anthropic, components of agent memory](https://anthropic.com/engineering/components-of-agent-memory)).

## External feedback beats intrinsic self-critique

The strongest finding across the literature is that **the evaluator, not the proposer, sets each loop's ceiling**. Huang et al. showed that earlier self-correction gains depended on oracle labels deciding when to stop. With oracle labels, GPT-3.5 on GSM8K rose from 75.9% to 84.3%. With intrinsic self-correction alone it *fell* to 74.7% after two rounds, because models flipped correct answers to wrong ones about as often as they fixed errors ([Huang et al., ICLR 2024](https://arxiv.org/abs/2310.01798); numbers via [arXiv HTML](https://arxiv.org/html/2310.01798v2)) *(snippet)*. At equal inference cost, plain self-consistency sampling beat multi-round self-correction. Kamoi et al.'s TACL survey reached the same conclusion: "no prior work demonstrates successful self-correction with feedback from prompted LLMs" on general tasks, self-correction "works well" with reliable external feedback such as code execution or search, and "the bottleneck is in the feedback generation" ([Kamoi et al.](https://arxiv.org/abs/2406.01297v3)). Zhang et al. report similar intrinsic failures on o1 and GPT-4o ([arXiv 2412.14959](https://arxiv.org/html/2412.14959v2)).

The positive results all rely on external signals. Reflexion's HumanEval jump from **80% to 91% pass@1** used test-execution feedback ([Reflexion](https://arxiv.org/pdf/2303.11366)) *(snippet)*. SWE-agent's lint-guarded edit command raised SWE-bench Lite resolution from **15.0% to 18.0%**, and from 10.3% with no dedicated editor ([SWE-agent, NeurIPS 2024](https://proceedings.neurips.cc/paper_files/paper/2024/file/5a7c947568c1b1328ccc5230172e1e7c-Paper-Conference.pdf)) *(secondary)*. Claude Code's docs encode the practitioner version: "Handing the same task to a subagent doesn't make the answer any better. A fresh reviewer does help, because it hasn't seen your reasoning" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The pattern holds across sessions too. SkillsBench found that self-generated skills gave **−1.3pp** on average while curated ones gave **+16.2pp**, and concluded that "models cannot reliably author the procedural knowledge they benefit from consuming" ([SkillsBench](https://arxiv.org/abs/2602.12670)) *(snippet)*. Voyager, by contrast, stores a skill only after it executes and passes a critic, and reports large gains ([Voyager](https://arxiv.org/abs/2305.16291)) *(not re-verified)*. The likely difference is verification.

| Signal rung (strongest first) | Example | Evidence |
|---|---|---|
| 1. Deterministic external verifier | Tests, type-check, lint, build exit code | Reflexion on HumanEval; SWE-agent lint ablation |
| 2. Tool-grounded critique | CRITIC with interpreter or search; `/verify` screenshots | Kamoi survey; [CRITIC](https://arxiv.org/abs/2305.11738) *(secondary)* |
| 3. Independent evaluator, fresh context | Reviewer subagent, `/code-review`, second session | Claude Code best-practices guidance |
| 4. Sampling plus vote or judge | Self-consistency, best-of-N | Huang et al. equal-cost comparison |
| 5. Same-context self-critique | Self-Refine | Huang; Kamoi; Zhang |

Two caveats keep this from being absolute. Frontier models since 2025 are RL-trained in agentic loops with test feedback, and Kamoi notes that "large-scale fine-tuning enables self-correction". The 2023 results are foundational but may be dated, and no controlled 2025–2026 study compares intrinsic and external correction on current coding agents. Self-critique also stays useful when the criteria are explicit and checkable by reading, such as spec coverage or style rules. There the value comes from the rubric, not from introspection. The design rule follows: **never let the model be the sole judge of its own success on a checkable task.**

## Within-turn loops ground each step in a signal

### 1. Act–observe tool loop (ReAct, CRITIC)

**What and why.** The agent interleaves reasoning with tool calls and feeds each observation into the next step. Anthropic defines agents as "typically just LLMs using tools based on environmental feedback in a loop" and calls it "crucial for the agents to gain 'ground truth' from the environment" at each step ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). ReAct reported +34% absolute on ALFWorld and +10% on WebShop ([ReAct](https://arxiv.org/abs/2210.03629)) *(not re-verified)*. Codex CLI runs the same loop over the Responses API, and an agent "could decide to make hundreds of tool calls in a single turn" ([OpenAI, Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop)). **How it fails.** Errors compound and costs grow, so Anthropic recommends stopping conditions such as maximum iterations. It also recommends poka-yoke tool design, such as requiring absolute paths after the model misused relative ones. **Recipe (from docs).** Give the agent a check. "The single most useful line in your `CLAUDE.md` is the command that runs it" ([best practices](https://code.claude.com/docs/en/best-practices)). `/verify` builds and runs the app, and `/run-skill-generator` teaches it how to launch your project ([Commands](https://code.claude.com/docs/en/commands)).

### 2. Edit-time verifier

**What and why.** A deterministic check runs right after every edit, so cheap syntax and type errors are caught before the expensive test loop. SWE-agent's linter-guarded edit was its most critical interface component, and **51.7% of trajectories** hit at least one rejected edit, which shows how often the guardrail fires *(secondary)*. Aider builds the loop in with `--auto-lint` (on by default), `--lint-cmd`, `--test-cmd` and `--auto-test`, and feeds non-zero output back to the model ([Aider lint/test docs](https://aider.chat/docs/usage/lint-test.html)) *(not re-verified; site unreachable)*. Cursor's "Iterate on Lints" fixes diagnostics on files the agent just edited, with roughly three iterations per file according to a staff forum reply ([Cursor forum](https://forum.cursor.com/t/iterate-on-lint-errors-feature/26304/3)). **How it fails.** Users report endless lint loops and "fixes" that break working code ([Cursor forum](https://forum.cursor.com/t/unrestricted-loop-of-linter-errors/36436)), so scope the linter to errors that matter. **Recipe (from docs).** A `PostToolUse` hook on edits; exit code 2 "shows stderr to Claude; the tool already ran" ([Hooks reference](https://code.claude.com/docs/en/hooks)):

```json
{ "hooks": { "PostToolUse": [ { "matcher": "Edit|Write",
    "hooks": [ { "type": "command", "command": "/path/to/lint-check.sh" } ] } ] } }
```

The costs docs add a related loop: a `PreToolUse` hook with `updatedInput` rewrites `npm test` or `pytest` to `… 2>&1 | tail -n 100` so that verbose test output doesn't flood context ([Costs](https://code.claude.com/docs/en/costs)).

### 3. Fresh-context reviewer (evaluator-optimizer)

**What and why.** One model generates and a separate one evaluates. Anthropic recommends this "when we have clear evaluation criteria, and when iterative refinement provides measurable value" ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). In Claude Code, `/code-review` "reviews the diff in a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code" ([best practices](https://code.claude.com/docs/en/best-practices)). **How it fails.** The critic can be over-eager. "A reviewer that's asked to find problems will always find *something*. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen." The fix is to scope the review to correctness against a spec and "skip style". **Recipe (from docs).** Create `.claude/agents/reviewer.md` with `tools: Read, Grep, Glob`. This gives "a reviewer that can't edit anything, and that limit is enforced by Claude Code rather than requested in a prompt". Use a prompt like "You're reviewing code you didn't write. Compare the changed files against the spec… check that every requirement is implemented and the listed edge cases have tests", set `model: haiku` for cheap passes, and invoke it with "have the reviewer compare the rate limiter against SPEC.md" ([best practices](https://code.claude.com/docs/en/best-practices)).

### 4. Parallel candidates plus filter (self-consistency, best-of-N, tree search)

**What and why.** Sample several attempts and keep the one that passes a filter. Self-consistency reported +17.9% on GSM8K with PaLM-540B ([Wang et al.](https://arxiv.org/abs/2203.11171)) *(not re-verified)*. Tree of Thoughts reported 74% against 4% for chain-of-thought on Game of 24 ([ToT](https://arxiv.org/abs/2305.10601)) *(not re-verified)*, and LATS reported 92.7% on HumanEval ([LATS](https://arxiv.org/abs/2310.04406)) *(secondary)*. Coding harnesses rarely run literal tree search. The practical version is **parallel worktrees, test filtering and git rollback**. `/batch` "splits the work into 5 to 30 units… each unit gets its own worktree and opens a PR" ([best practices](https://code.claude.com/docs/en/best-practices)). DGM independently discovered "generate several candidates and rank them" as an improvement to its own harness *(not re-verified)*. **How it fails.** Cost grows with each branch, and when an LLM estimates the value of a branch, that estimate inherits self-evaluation weaknesses. **Recipe (untested sketch).** For a hard fix, ask Claude to try three approaches in separate worktrees, run the same failing test in each, and present the passing candidates ranked by diff size for you to choose.

### 5. Intrinsic self-critique (Self-Refine)

Self-Refine generates, critiques and refines with one model and no external signal. It reported about 20% average improvement across seven tasks ([Madaan et al.](https://arxiv.org/abs/2303.17651)) *(not re-verified)*. It works mostly on open-ended quality tasks with explicit criteria, and it is the bottom rung of the signal ladder for reasoning. It belongs in the taxonomy mainly as the **anti-pattern to replace**. If you use it, attach an explicit checklist (the spec, a style guide) so the rubric does the work, and never let it decide whether a checkable task is done.

## Within-session loops move "keep going" from the prompt into the harness

### 6. Completion gates (Stop hooks, `/goal`, TaskCompleted)

**What and why.** The harness refuses to let the agent stop until a condition holds. This addresses the most common failure: "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually *is* done, 'looks done' is all it has to go on. In practice that makes you the test suite" ([best practices](https://code.claude.com/docs/en/best-practices)). The docs give a strictness ladder: an instruction in the prompt, then `/goal` (a separate model checks a condition after every turn), then a Stop hook ("the turn doesn't end until the typecheck passes or the block limit is reached"), then an independent review. They also retire prompt nagging such as "keep going, don't be lazy", which is "more likely to cause over-work than fix a stall". **How it fails.** Gates fail in three ways. The loop never terminates, which Claude Code guards against with `stop_hook_active` and an **8-consecutive-continuation cap** that resets whenever Claude calls a tool and is adjustable via `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` ([Hooks reference](https://code.claude.com/docs/en/hooks)). The agent claims "done" without evidence ("'All tests pass' on its own tells you very little"). And the agent games the gate. ImpossibleBench builds tasks whose tests contradict the spec, so any pass means cheating, and found cheating rates of roughly **39–76%** across frontier models ([ImpossibleBench](https://arxiv.org/html/2510.20270v1)) *(snippet; per-model mapping unconfirmed)*. A prompt line telling the model to stop if tests look flawed cut GPT-5's hacking on one variant from about 93% to 1% ([LessWrong summary](https://www.lesswrong.com/posts/qJYMbrabcQqCZ7iqm/impossiblebench-measuring-reward-hacking-in-llm-coding-1)). Hiding tests cut hacking to near zero but significantly hurt legitimate performance. EvilGenie counters that many "hacks" are fixes to genuinely wrong tests ([EvilGenie](https://arxiv.org/pdf/2511.21654)).

**Recipe (from docs).** A Stop hook where "exit code 2 is what blocks the stop" and stderr becomes the reason ([best practices](https://code.claude.com/docs/en/best-practices)):

```json
{ "hooks": { "Stop": [ { "hooks": [
    { "type": "command", "command": "pnpm tsc --noEmit 1>&2 || exit 2" } ] } ] } }
```

Other documented variants: `/goal all tests in tests/auth pass and lint is clean`, which wraps "a session-scoped prompt-based Stop hook" judged by a small fast model that cannot run tools ([Goal docs](https://code.claude.com/docs/en/goal)). A `type: "prompt"` Stop hook that returns `{"ok": false, "reason": …}` or `{"impossible": true}`. An experimental `type: "agent"` Stop hook ("Verify that all unit tests pass. Run the test suite and check the results. $ARGUMENTS", timeout 120) that can run tools for up to 50 turns; the docs say "for production, prefer command hooks". And a `TaskCompleted` script that runs `npm test` and exits 2 to keep a task open ([Hooks reference](https://code.claude.com/docs/en/hooks)). **Add-on (untested sketch).** Pair any "tests pass" gate with a permission deny rule or a `PreToolUse` block on edits to test directories and fixtures, plus the ImpossibleBench-style instruction in CLAUDE.md: "If a test contradicts the spec, stop and report it; never edit or special-case tests to pass." A gate that only checks "tests pass" rewards tampering with the tests.

### 7. State-on-disk iteration (Ralph, long-running harnesses)

**What and why.** Rerun the same prompt in a fresh context until the work is done, keeping all state in files. Geoffrey Huntley's July 2025 formulation is "Ralph is a Bash loop" ([DreamHost explainer](https://www.dreamhost.com/blog/ralph-wiggum/); [Steve Kinney](https://stevekinney.com/writing/the-ralph-loop)) *(original post unreachable)*. Each iteration takes one item from a plan file and must satisfy "backpressure" (tests, type-checks, builds). Because no single context grows without bound, the loop sidesteps context rot. The Register reported it being used to "vibe-clone commercial software for $10 an hour" ([The Register, 2026-01-27](https://www.theregister.com/2026/01/27/ralph_wiggum_claude_loops/)). This is effectively Reflexion memory persisted on disk. Anthropic's long-running harness is the structured version ([Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). An initializer session creates `init.sh`, `claude-progress.txt` and a JSON feature list (200+ features for a claude.ai clone, all initially failing). Each later session reads git log and progress notes, runs a smoke test, completes one feature, commits, and updates progress. Agents may flip only `passes`, and JSON was chosen because the model is "less likely to inappropriately change or overwrite JSON" than Markdown. **How it fails.** Without a completion criterion or cap the loop runs forever. Weak specs cause drift. Agents read earlier progress and declare victory early. The official plugin runs inside one session through a Stop hook, so it **gives up the fresh-context property** that makes the bash loop work ([DeepWiki](https://deepwiki.com/anthropics/claude-code/4.5-ralph-wiggum-plugin)). **Recipe (plugin from docs; bash loop an untested sketch).** The plugin's README example is `/ralph-loop "<task>" --completion-promise "COMPLETE" --max-iterations 50`, and the README advises always setting `--max-iterations` ([ralph-loop README](https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/plugins/ralph-loop/README.md)). Sources disagree on the install name (`ralph-loop` or `ralph-wiggum` at `claude-plugins-official`). For fresh context, use a bash loop:

```bash
# untested sketch: fresh context per iteration, hard cap, file-based exit
for i in $(seq 1 20); do
  claude -p "$(cat PROMPT.md)" --permission-mode acceptEdits --max-turns 40 --max-budget-usd 3
  grep -q '^DONE' progress.md && break
done
```

PROMPT.md should say: pick the highest-priority unchecked item in `fix_plan.md`, implement it, run the tests, update `progress.md` and the plan, commit, and write `DONE` on the first line of `progress.md` when nothing remains. For most in-session "keep going until X" needs, `/goal` now replaces a hand-rolled Ralph Stop hook.

### 8. Context steering (compaction, notes, subagents)

**What and why.** Long sessions degrade. Chroma's July 2025 study of 18 models over 194,480 calls found performance "grows increasingly unreliable as input length grows", even on trivial tasks ([Chroma, Context Rot](https://trychroma.com/research/context-rot)); note that Chroma sells a vector database. Anthropic's answer has three parts: compaction that "preserves architectural decisions, unresolved bugs, and implementation details", structured notes "persisted to memory outside of the context window", and subagents that return "a condensed, distilled summary… (often 1,000-2,000 tokens)" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Current Claude Code has a 1M-token window on most models, so "you'll rarely run out of context", but `/clear` between tasks is still recommended "because a focused context gets you better answers and costs less" ([best practices](https://code.claude.com/docs/en/best-practices)). **How it fails.** Compaction drops important instructions: "the sentence can get lost when the conversation compacts, so anything that matters belongs in a deny rule". `/compact` "is itself a big request". **Recipe (manual command from docs; hook an untested sketch).** Run `/compact keep the API changes and the test commands` manually. Or, because a `PreCompact` hook's stdout "becomes instructions for the compaction summary" (under 10,000 characters), and `PostCompact` receives `compact_summary` ([Hooks reference](https://code.claude.com/docs/en/hooks)):

```json
{ "hooks": { "PreCompact": [ { "hooks": [ { "type": "command",
  "command": "echo 'Preserve: current plan, failing test names, files touched, user corrections and rejected approaches.'" } ] } ] } }
```

A `PostCompact` hook can then append `compact_summary` to a session log for later distillation (pattern 10).

### 9. Interval loops (`/loop`, `/autofix-pr`)

**What and why.** Rerun a prompt on a timer inside an open session, for example `/loop 15m check CI on this branch, and if it's red pull the failing job's log, fix it and push` ([best practices](https://code.claude.com/docs/en/best-practices)). Without an interval, `/loop` self-paces between 1 minute and 1 hour. A bare `/loop` runs a maintenance prompt (finish unfinished work, then tend PR comments, CI and conflicts, then clean up) or your `.claude/loop.md` ([Scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)). `/autofix-pr` spawns a cloud session that watches the PR and pushes fixes for CI failures and review comments ([Commands](https://code.claude.com/docs/en/commands)). **How it fails.** Background loops "keep sending requests while you aren't typing" ([best practices](https://code.claude.com/docs/en/best-practices)). Tasks fire only while the session is open and idle, have no catch-up, expire after 30 days, and are capped at 50 per session ([Scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)). `/usage` shows per-`/loop` token rows so you can see what a loop costs ([Costs](https://code.claude.com/docs/en/costs)). **Recipe (from docs).** Use `/loop 20m /review-pr 1234` to rerun a skill each iteration. This works only for skills Claude may invoke itself, so not those with `disable-model-invocation: true`.

## End-of-session loops turn one session's lessons into durable files

### 10. Correction capture into instruction files and memory

**What and why.** This is the most widely practiced cross-session loop. Practitioners have converged on two layers ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). The first is a **human-curated, version-controlled instruction file** (CLAUDE.md, AGENTS.md, `.claude/rules/`). The official criteria for adding a line are: "Claude makes the same mistake a second time", "a code review catches something Claude should have known", "you type the same correction… that you typed last session", or "a new teammate would need the same context". The second is an **agent-written memory layer**. Claude Code's auto memory saves `user`, `feedback` ("corrections you give Claude and approaches you confirm"), `project` and `reference` notes to `~/.claude/projects/<project>/memory/`, with a `MEMORY.md` index of which the first 200 lines or 25KB load at session start. Boris Cherny's team reportedly adds to a shared CLAUDE.md "anytime Claude does something incorrectly", and in code review tags `@claude` on PRs to add the lesson ([InfoQ](https://www.infoq.com/news/2026/01/claude-code-creator-workflow)) *(secondary; original X posts not fetched)*. Every's Compound Engineering formalizes the loop as brainstorm → plan → work → review → "capture the learning into `docs/solutions/` so the next loop starts smarter" ([compound-engineering README](https://raw.githubusercontent.com/EveryInc/compound-engineering-plugin/HEAD/README.md)). The research roots are ExpeL, which extracts natural-language insights from success/failure pairs and maintains them with ADD/EDIT/UPVOTE/DOWNVOTE operations, dropping insights whose votes reach zero ([ExpeL](https://arxiv.org/abs/2308.10144)) *(not re-verified)*, and Generative Agents' periodic reflection ([Park et al.](https://arxiv.org/abs/2304.03442)) *(not re-verified)*.

**Why it works, and how to write memory well.** Anthropic's memory experiments add a counterintuitive point: **tell the model what memory is for, not how to use it**. A prescriptive "record only failures" rule *reduced* the memory gain by 0.234 on Opus 5 and 0.150 on Opus 4.7. Weaker models also skip reading memory. Sonnet 4.6 read it less than half the time, and prompting it to read memory first nearly doubled its CL-Bench score from 0.330 to 0.641 ([components of agent memory](https://anthropic.com/engineering/components-of-agent-memory)). This explains why injected context (CLAUDE.md, the MEMORY.md index) is more reliable than memory the agent must choose to fetch. **How it fails.** Bloat: "longer files consume more context and reduce adherence", so target under 200 lines. Contradictions: Claude "may pick one arbitrarily". Overfitting to one-off corrections. And poisoning through automatic write paths, which is the biggest risk. The vendor trend points the same way. Cursor staff say Memories were intentionally removed in 2.1.x, with users told to export them into Rules ([Cursor forum](https://forum.cursor.com/t/are-my-memories-gone/144057)). Current Cursor docs and a 3.8 changelog describe a reworked memories feature with automation-driven pruning ([Cursor 3.8 changelog](https://cursor.com/changelog/06-18-26)) *(both snippet-level; the sources conflict)*. Windsurf now labels its Cascade memories legacy and recommends rules or AGENTS.md ([Windsurf docs](https://docs.windsurf.com/windsurf/cascade/memories.md)) *(snippet)*. Durable knowledge is moving into reviewable files.

**Recipes.** Team loop *(from docs plus secondary practice)*: run `/install-github-app`, then comment `@claude add a rule to CLAUDE.md so this doesn't happen again` on PRs. Compound Engineering *(from README)*: `/plugin marketplace add EveryInc/compound-engineering-plugin`, then `/plugin install compound-engineering`, then run `/ce-plan`, `/ce-work` and `/ce-compound` per feature. Personal reflect skill *(untested sketch; uses documented skill frontmatter and `` !`cmd` `` injection)*:

~~~markdown
---
name: reflect
description: Review this session's corrections and propose CLAUDE.md or rules edits
disable-model-invocation: true
---
Review this session for corrections I gave, approaches I confirmed, and mistakes you repeated.
Keep only items seen at least twice or that I explicitly flagged.
For each, pick the narrowest home: ./CLAUDE.md, a path-scoped .claude/rules/ file, a skill,
or CLAUDE.local.md. Prefer editing or merging an existing line over appending.
Keep CLAUDE.md under 200 lines. Show diffs and wait for approval before writing.
Current CLAUDE.md:
!`cat CLAUDE.md`
~~~

Auto memory already captures `feedback` notes from corrections. Decide which layer owns which lesson so the same lesson is not written twice: preferences in auto memory, team rules in CLAUDE.md.

### 11. Skill distillation and evaluation

**What and why.** Turn a procedure that worked into a reusable, retrievable capability. Voyager stored verified JavaScript skills indexed by description embeddings and reported 3.3× more unique items and tech-tree milestones up to 15.3× faster ([Voyager](https://arxiv.org/abs/2305.16291)) *(not re-verified)*. LATM split a strong tool-maker from a cheap tool-user ([LATM](https://arxiv.org/abs/2305.17126)) *(not re-verified)*. Agent Workflow Memory induced reusable workflows, with relative gains of about 24.6% on Mind2Web and 51.1% on WebArena ([AWM](https://arxiv.org/abs/2409.07429)) *(not re-verified)*. Anthropic's Agent Skills (SKILL.md, October 2025, an open standard since December 2025) rely on **progressive disclosure**: names and descriptions are preloaded, bodies load when relevant, and linked files load only on demand ([Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)). Codex adopted the same format, with user skills in `~/.codex/skills/` and a bundled skill-creator ([Codex Skills](https://developers.openai.com/codex/skills)) *(snippet)*. The March 2026 skill-creator upgrade turned this into an eval loop ([Improving skill-creator](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills)). It writes test prompts and expected-output descriptions, runs a benchmark mode tracking pass rate, time and tokens, runs parallel clean-context eval agents, uses blind comparator A/B tests (v1 vs v2, or skill vs no skill), and optimizes the description, which improved triggering on 5 of 6 public document skills.

**How it fails.** Cold-start authoring doesn't help (SkillsBench −1.3pp), though SkillEvolBench argues that experience-derived skills deserve separate study ([SkillEvolBench](https://arxiv.org/html/2605.24117)) and MUSE-Autoskill reports modest gains, 44.80% to 47.52% for Codex ([MUSE-Autoskill](https://arxiv.org/pdf/2605.27366)) *(both snippet)*. A SoK notes the negative result "derive[s] primarily from a single, non-peer-reviewed benchmark" ([SoK](https://arxiv.org/pdf/2602.20867)). Other failure modes: trigger confusion and sprawl, obsolescence ("capability uplift" skills "may become less necessary as models improve", while "encoded preference" skills last longer), and supply-chain attacks (see failure modes below). **Recipe (untested sketch on documented skill-creator features).** After a multi-step task succeeds *and* verification passes, ask Claude to use skill-creator to turn it into `.claude/skills/<name>/`, with deterministic steps moved into `scripts/`. Have it write 3–10 evals, including near-miss prompts that should *not* trigger. Keep the skill only if the comparator shows it beats no-skill on pass rate or tokens. Commit it via PR. After every model upgrade, rerun the benchmark with the skill disabled, and delete capability-uplift skills the base model now passes. `/skill-doctor` reports per-skill context cost and usage frequency to guide pruning ([Skills docs](https://code.claude.com/docs/en/skills)).

### 12. Post-session audit (slow steps, failures, friction)

**What and why.** After a session or a batch of sessions, mine transcripts for wasted time and friction, and route each finding to a fix. Claude Code ships `/insights`, which writes an HTML report of "which projects you work in, how you use Claude Code, where things go wrong, and features to try". It analyzes up to 200 not-yet-seen sessions per run, surfaces "friction points such as misunderstood requests or buggy code", writes to `~/.claude/usage-data/report.html`, counts against your plan, and is not available in cloud sessions ([Costs](https://code.claude.com/docs/en/costs); [Commands](https://code.claude.com/docs/en/commands)). Third-party guides describe roughly a 30-day window and suggested CLAUDE.md rules ([Pillitteri](https://pasqualepillitteri.it/en/news/408/claude-code-insights-workflow-command)) *(secondary)*. A v2.1.281 addition reportedly estimates how many permission prompts auto mode could have absorbed ([Nerdschalk](https://nerdschalk.com/claude-code-shows-where-recent-sessions-ran-into-trouble/)) *(secondary, unconfirmed)*. `/insights` runs over a batch of sessions, so a true per-session audit needs a `SessionEnd` hook. Transcripts are JSONL at `~/.claude/projects/<project>/<session-id>.jsonl`, kept 30 days by default (`cleanupPeriodDays`). Anthropic warns that "the entry format is internal… scripts that parse these files directly can break on any release", and recommends `claude -p --resume <id> --output-format json`, `/export`, the hook's `transcript_path`, or the Agent SDK ([Sessions](https://code.claude.com/docs/en/sessions)). Community tools include claude-code-log for HTML rendering and ccusage for cost ([claude-code-log](https://awesome.ecosyste.ms/projects/github.com%2Fdaaain%2Fclaude-code-log); [ccusage](https://www.mintlify.com/ryoppippi/ccusage/family/overview)).

**Signals worth extracting** *(researcher inference)*: repeated identical tool errors (3 or more), mapped to a CLAUDE.md note or tool fix; permission prompts on read-only commands, mapped to an allowlist; correction or frustration turns, interrupts and rewinds, mapped to a rule or skill; long gaps or long Bash runs, mapped to background commands or faster test targets; compactions per session, mapped to subagents or a shorter CLAUDE.md; and abandoned sessions. **How it fails.** `SessionEnd` "can't block" and has a **1.5-second default timeout** (raise it per hook up to 60 s, or with `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS`) ([Hooks reference](https://code.claude.com/docs/en/hooks)). Heavy analysis must therefore be detached or deferred. An agent auditing its own transcript may under-report its own failures, so anchor the audit on objective counts before any LLM judgment. And reports that nobody acts on change nothing.

**Recipe (untested sketch).** Log tool timing cheaply with async hooks, archive each transcript at session end, and run a detached retrospective:

```json
{ "hooks": {
  "PreToolUse":  [ { "hooks": [ { "type": "command", "async": true,
    "command": "jq -c '{ts: now, e: .hook_event_name, id: .tool_use_id, tool: .tool_name}' >> ~/.claude/tool-timing.jsonl" } ] } ],
  "PostToolUse": [ { "hooks": [ { "type": "command", "async": true,
    "command": "jq -c '{ts: now, e: .hook_event_name, id: .tool_use_id, tool: .tool_name}' >> ~/.claude/tool-timing.jsonl" } ] } ],
  "SessionEnd":  [ { "hooks": [ { "type": "command", "timeout": 10,
    "command": "~/.claude/hooks/archive-and-retro.sh" } ] } ] } }
```

```bash
#!/bin/bash
# ~/.claude/hooks/archive-and-retro.sh  (untested sketch)
INPUT=$(cat)
SRC=$(jq -r '.transcript_path' <<<"$INPUT"); SID=$(jq -r '.session_id' <<<"$INPUT")
mkdir -p ~/agent-archive && cp "$SRC" ~/agent-archive/"$SID".jsonl
# --bare keeps the child from re-running this SessionEnd hook recursively (it requires ANTHROPIC_API_KEY)
nohup claude --bare -p "Read ~/agent-archive/$SID.jsonl. List repeated tool failures, slow steps, \
permission prompts and user corrections, with evidence. Propose at most 2 CLAUDE.md rules. \
Append the result to ~/agent-archive/retros.md." \
  --allowedTools "Read,Write" --permission-prompts none --max-budget-usd 0.50 \
  --no-session-persistence >/dev/null 2>&1 &
exit 0
```

Pair the pre/post timing lines by `tool_use_id` in the weekly job to find the slowest tools. The researchers inferred the recursion risk. A non-`--bare` `claude -p` loads project hooks, including this `SessionEnd` hook, so use `--bare` or an environment-variable guard. The docs do confirm that a `SessionEnd` hook "can archive the transcript".

## Periodic loops mine many sessions, then gate changes on evals

### 13. Friction mining into harness config

**What and why.** Today, a "self-modifying harness" mostly means the agent proposes edits to its own **configuration surface**: CLAUDE.md, rules, skills, subagent definitions, hooks and permission allowlists. It works from transcript evidence, and a human reviews the diff. The canonical first-party loop is `/fewer-permission-prompts`: "Scan your transcripts for common read-only Bash and MCP tool calls, then add a prioritized allowlist to project `.claude/settings.json`" ([Commands](https://code.claude.com/docs/en/commands)). One write-up saw it scan 50 recent sessions (565 Bash and 52 MCP calls), limit itself to read-only commands and prefer specific commands over wildcards ([Classmethod](https://dev.classmethod.jp/en/articles/claude-code-fewer-permission-prompts/)) *(secondary)*. `/usage` attributes tokens to skills, subagents, plugins and MCP, offers recommendations such as "Trim ~/code/api/CLAUDE.md · 49k tokens per request", and applies fixable ones when you press `f` (v2.1.305+) ([Costs](https://code.claude.com/docs/en/costs)). This is the low-cost, low-risk cousin of DGM. The mutable surface is declarative config instead of arbitrary Python, and the fitness signal is friction instead of a benchmark. **How it fails.** Agent-authored allowlists need review. A bug, fixed in May 2026, made the skill silently drop commands prefixed with environment-variable assignments ([issue mirror #51057](https://claudeissues.com/issue/51057-bug-fewer-permission-prompts-drops-commands-prefixed-with-environment-variable-a)). Privilege also creeps: every allowlist entry and hook widens what runs unattended. A GitHub issue still requests a native learning loop ([anthropics/claude-code#57830](https://github.com/anthropics/claude-code/issues/57830)).

**Recipe (untested sketch).** Run a weekly local bottleneck report. It has to run locally because transcripts and auto memory are machine-local, and cloud scheduled tasks run on a fresh clone without them.

```bash
# run_audit.sh — crontab: 0 9 * * MON ~/audit/run_audit.sh
python3 ~/audit/prepass.py --days 7 --out ~/audit/weekly_stats.json   # counts tool calls, errors,
#   repeated errors, compactions, correction phrases, interrupts, durations; samples 20 worst sessions
claude --bare -p "$(cat ~/audit/audit_prompt.md)" --allowedTools "Read,Write" \
  --permission-prompts none --output-format json --max-budget-usd 2 --no-session-persistence
```

The prompt says: cluster the friction into at most 5 bottlenecks ranked by frequency × time lost; give session IDs as evidence, a root-cause hypothesis and one concrete fix each; and route each fix by type. Repeated permission prompts go to `/fewer-permission-prompts` (read-only only). Repeated corrections become a CLAUDE.md rule. A rule violated twice more becomes a proposed `PreToolUse`/`PostToolUse` hook. Repeated long research subtasks become a `.claude/agents/<name>.md` subagent. Repeated manual API lookups become a proposed MCP server. Write proposals as one diff that is never auto-merged, and track whether last week's fixes moved their target metric. Parse JSONL defensively because the format is unstable. The researchers assembled this recipe; Anthropic has published no "weekly transcript audit".

### 14. Memory consolidation and pruning

**What and why.** Memory that only grows eventually stops working. Consolidation runs offline, checks notes against ground truth, merges duplicates and demotes detail. ACE names the two failure modes it fixes. **Brevity bias** is optimizers collapsing toward short, generic prompts. **Context collapse** is when an LLM that "fully rewrit[es] the accumulated context at each adaptation step" compresses it "into much shorter, less informative summaries" ([ACE](https://arxiv.org/html/2510.04618v2)) *(snippet)*. ACE's Curator emits itemized delta updates, each bullet with an ID and `helpful`/`harmful` counters. It reports +10.6% on AppWorld, +8.6% on finance tasks, and 86.9% lower adaptation latency ([ACE repo](https://github.com/ace-agent/ace)). Anthropic's "dreaming" tests notes against transcripts, rewrites wrong ones, merges duplicates and builds wiki links. Wiki scores on a 350,000-file corpus rose from **13% to 48% over 128 dreaming sessions**, and in a Pokémon run a corrected note got the agent past Mt. Moon, which the raw note never managed ([components of agent memory](https://anthropic.com/engineering/components-of-agent-memory)). Letta's sleep-time compute reported about 5× less test-time compute for equal accuracy, though its benchmarks measure reasoning cost rather than consolidation itself ([Letta](https://letta.com/blog/sleep-time-compute)). Conflict handling has research precedents too: Mem0's ADD/UPDATE/DELETE/NOOP decisions ([Mem0](https://arxiv.org/abs/2504.19413)) and Zep's bi-temporal invalidation of superseded facts ([Zep](https://arxiv.org/abs/2501.13956)) *(both not re-verified, vendor-authored)*.

**How it fails.** Consolidation creates its own failures. A dreaming wiki grew to **1.77× its source corpus**. Concurrent writers to one table kept only 41 of 57 facts, against 57 of 57 with one writer per page. Sonnet 3.7 deleted nine files during a costly reorganization. "An incorrect injected note… can be carried into every session" ([Anthropic](https://anthropic.com/engineering/components-of-agent-memory)). **Built-in aids (from docs).** Claude Code warns when MEMORY.md nears its limits and tells Claude to "merge or drop stale entries", records `modified` timestamps on memory files, and offers `/doctor prompt-audit` (v2.1.283+) to find outdated or conflicting instructions across CLAUDE.md, rules, skills and subagents ([memory docs](https://code.claude.com/docs/en/memory)). The memory tool docs advise "periodically delete memory files that haven't been accessed in a long time" ([Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). **Recipe (untested sketch).** Run a weekly GitHub Actions job for repo-level rules:

```yaml
on: { schedule: [ { cron: "0 9 * * 1" } ] }
jobs:
  consolidate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: >
            Audit CLAUDE.md and .claude/rules/. Merge duplicates, delete lines contradicted by
            current code, move multi-step procedures into skills and file-specific rules into
            path-scoped rules, keep CLAUDE.md under 200 lines. Edit in place (no full rewrite);
            give each removal a one-line reason. Propose the result as a branch for review.
          claude_args: "--max-turns 30"
```

This follows the docs' scheduled-workflow shape (`prompt` puts the action in automation mode). Add the job permissions your repo needs. Consolidate auto memory locally, because it is machine-local. A sound checklist: gate writes on repetition, choose the narrowest scope, edit rather than append, record provenance, and keep one writer per file. ACE-style evidence counters, such as tracking which CLAUDE.md lines were cited or violated, are a clear gap: research has them, but practitioner tools rarely do.

### 15. Transcript mining at scale (Clio-style)

**What and why.** Hierarchical LLM clustering over many sessions shows patterns no single transcript reveals. Anthropic's Clio, now "Anthropic Insights", runs four steps: per-conversation facet extraction, semantic clustering, privacy-scrubbed cluster summaries, and a navigable hierarchy. Across 1M conversations it found web and mobile development as the largest category (over 10%), uncovered an SEO-spam network that broke no single-conversation rule, and correlated with existing classifiers at r = 0.71 ([Clio](https://www.anthropic.com/research/clio)). LangSmith's Insights Agent clusters production traces without predefined categories and can focus on thumbs-down traces ([LangChain blog](https://blog.langchain.com/insights-agent-multiturn-evals-langsmith)). Braintrust Topics classifies logs by intent, sentiment and issue, then clusters them, with one page citing UMAP + HDBSCAN + c-TF-IDF ([Braintrust Topics](https://braintrust.dev/docs/observe/topics)). An MSR 2026 study of 33,580 agentic PRs found reverts stem mainly from scope management and contextual understanding rather than functional bugs ([MSR 2026](https://2026.msrconf.org/details/msr-2026-mining-challenge/27/)) *(snippet)*. **How it fails.** Agent transcripts contain secrets, customer data and code. Clio's mitigations carry over: omission instructions, minimum cluster sizes, an LLM audit of summaries before humans see them, and restricted access. Anthropic concedes that safeguards "might miss some private information". **Recipe (untested sketch).** Run a monthly team "Clio-lite". Archive transcripts centrally via `SessionEnd`. Extract per-session facets with a cheap model under `claude -p --json-schema` (task type, outcome, first failure point, erroring tools, correction count, permission prompts, duration, cost). Cluster the "first failure" text. Have an LLM name each cluster and check it for PII. Drop clusters below a minimum size. Rank by frequency × cost, and file the top 3–5 as tickets with exemplar session IDs. Those clusters feed pattern 16.

### 16. Error-analysis eval flywheel

**What and why.** Evals turn one-off fixes into protection that compounds. Anthropic's January 2026 guidance is concrete ([Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). "20-50 simple tasks drawn from real failures is a great start." Separate capability evals, which should start at a low pass rate, from regression evals near 100%, and graduate saturated capability evals into regression suites. Prefer code graders, calibrate model graders against humans, and grade "what the agent produced, not the path it took". Use pass@k when one success suffices and pass^k when consistency matters: 75% per-trial success gives pass^3 ≈ 42%. "Read the transcripts!" A 0% pass rate usually signals a broken task or grader, "not an incapable agent". The Claude Code team itself added evals for concision, file edits and later over-engineering, and these fed production monitoring and A/B tests. The qualitative front end is open coding (note the first failure in each trace) followed by axial coding (group the notes into a taxonomy) ([course summary](https://www.designgurus.io/course-play/grokking-llm-evals/doc/open-coding-notes-on-what-went-wrong)) *(secondary)*. Hamel Husain's guidance adds: review about 100 traces or until no new failure types appear, have one domain expert own the labels, use binary judges, and validate judges by TPR/TNR ([hamel.dev evals FAQ](https://hamel.dev/blog/posts/evals-faq/)) *(not re-verified)*. **How it fails.** Grader bugs dominate scores: CORE-Bench went from **42% to 95%** for Opus 4.5 after grading fixes. Evals saturate. And Shankar et al. found "criteria drift": grading outputs changes what people want, so "evaluation criteria cannot be fully fixed before humans judge outputs" ([Who Validates the Validators?](https://arxiv.org/abs/2404.12272)). **Recipe (untested sketch).** Run a CI eval gate on PRs that touch CLAUDE.md, skills, hooks, prompts or model config:

```bash
for task in evals/tasks/*/; do
  for k in 1 2 3; do
    work=$(mktemp -d); cp -r "$task/fixture/." "$work"; cp -r CLAUDE.md .claude "$work"/
    (cd "$work" && claude -p "$(cat "$task/prompt.md")" --permission-mode dontAsk \
       --allowedTools "Read,Edit,Bash(npm test *)" --max-turns 30 --max-budget-usd 1 \
       --output-format json > run.json)
    "$task/grade.sh" "$work" && r=pass || r=fail
    echo "$task,$k,$r" >> results.csv
  done
done   # then compute pass@3 / pass^3 and cost; fail the job if the regression suite drops
```

Do **not** use `--bare` here when the change under test is CLAUDE.md, skills or hooks, because `--bare` skips all of them. Run the job in a sandboxed runner, because a non-bare `claude -p` runs project hooks and MCP servers "even in a folder you've never trusted" ([Headless](https://code.claude.com/docs/en/headless)).

### 17. Automated prompt and program optimization

**What and why.** Once a metric and a labeled set exist, search replaces hand-tuning. GEPA (ICLR 2026 oral) reads execution traces in natural language, proposes edits and keeps a Pareto frontier. Its v2 reports **+6pp over GRPO RL with up to 35× fewer rollouts** and more than 10pp over MIPROv2, mostly on Qwen3 8B and evaluated by the authors; v1's headline numbers differ ([GEPA](https://arxiv.org/abs/2507.19457)) *(snippet)*. GEPA is the automated form of the human "read transcripts, fix the prompt" loop, which explains its sample efficiency. The older family includes APE and OPRO (generate-and-score; OPRO feeds past prompts and scores into a meta-prompt), ProTeGi (textual gradients plus beam search), TextGrad (critiques backpropagated through a computation graph), Trace and PromptWizard ([comparison, arXiv 2506.00400](https://arxiv.org/html/2506.00400v3)). DSPy wraps these as optimizers. The guidance, which could not be re-checked, is BootstrapFewShot for about 10 examples, MIPROv2 for 200+, and `dspy.GEPA` when the metric can return textual feedback ([DSPy optimizers](https://dspy.ai/learn/optimization/optimizers/)) *(not re-verified)*. ACE reports 75.1% fewer rollouts than GEPA for context adaptation ([ACE repo](https://github.com/ace-agent/ace)). Claude Code exposes eval-driven prompt iteration through `/claude-api … prompt-audit|build-eval|hillclimb` ([Skills docs](https://code.claude.com/docs/en/skills)). **How it fails.** It overfits the eval set (Goodhart). Budgets differ so much between reimplementations that cross-paper numbers are not comparable. And no independent, same-budget benchmark on agentic coding tasks exists. **Recipe (untested sketch).** Use pattern 16's dataset as train/val and its graders as the metric. Freeze a held-out split the optimizer never sees. Optimize one surface at a time (a skill's instructions, a subagent prompt, a tool description). Accept a candidate only if it beats the baseline on the held-out split *and* passes the regression suite. Ship it via canary (pattern 19), and version every prompt.

### 18. Automated agent and harness design (offline R&D)

**What and why.** These systems search over the agent itself. There are two families. **Meta-agent search** has a separate agent write or evolve designs: ADAS reported +13.6 F1 on DROP and +14.4% on MGSM ([ADAS](https://arxiv.org/abs/2408.08435)); AFlow runs MCTS over workflow graphs, reporting +5.7% and small models beating GPT-4o at 4.55% of the cost ([AFlow](https://arxiv.org/abs/2410.10762)); Promptbreeder also evolves its mutation prompts ([Promptbreeder](https://arxiv.org/abs/2309.16797)) *(all not re-verified)*. AlphaEvolve evolves codebases against automated evaluators and reportedly recovers about 0.7% of Google's worldwide compute ([DeepMind](https://deepmind.google/discover/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)) *(not re-verified)*. It became generally available on Google Cloud in July 2026 ([Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/alphaevolve-is-available-for-everyone)) *(snippet)*. **True self-reference** has the agent edit its own code. STOP ran a scaffold-improver on itself ([STOP](https://arxiv.org/abs/2310.02304)), and Gödel Agent monkey-patches its own logic ([Gödel Agent](https://arxiv.org/abs/2410.04444)) *(both not re-verified)*. SICA went from **17% to 53%** on a SWE-bench Verified subset by editing its own codebase ([SICA](https://arxiv.org/abs/2504.15228v2)) *(snippet)*. The Darwin Gödel Machine keeps an archive, samples parents beyond the top scorer, and validates children empirically, rising from **20% to 50%** on SWE-bench and 14.2% to 30.7% on Polyglot ([DGM](https://arxiv.org/abs/2505.22954)) *(not re-verified; consistent with [The Decoder](https://the-decoder.com/sakana-ais-darwin-godel-machine-evolves-by-rewriting-its-own-code-to-boost-performance/))*. The Huxley-Gödel Machine identifies a "metaproductivity-performance mismatch": an agent's own score poorly predicts how good its descendants will be. It therefore selects by clade-level descendant success with Thompson sampling, and beats DGM and SICA with less compute ([HGM, ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/hash/821d20219c2f14850af1b5220f0ed13f-Abstract-Conference.html)) *(snippet)*. Hyperagents (DGM-H) make the improvement procedure itself editable, and the meta-level skills it finds transfer across domains ([Hyperagents](https://arxiv.org/abs/2603.19461)) *(snippet)*.

**Why it matters for practitioners.** DGM's discoveries are mostly known harness engineering rediscovered: granular file viewing, string-replace edits, patch validation, multiple candidates with ranking, and a memory of failed attempts. These loops amount to **automated harness tuning for a given model and benchmark**. They take days of wall-clock time and a high API bill per run (the researchers recalled about two weeks and roughly USD 22k for one DGM run; unverified), which makes them offline R&D. **How it fails.** DGM node 114 "removed the logging of special tokens that indicate tool usage (despite instructions not to change the special tokens), effectively bypassing our hallucination detection function". Hacking was more frequent when detection functions were visible ([DGM PDF](https://arxiv.org/pdf/2505.22954); [The Register](https://www.theregister.com/2025/06/02/self_improving_ai_cheat/)) *(snippet)*. STOP's improvers sometimes disabled a sandbox flag *(not re-verified)*. **Recipe (untested sketch, generic harness).** Put the scaffold in git, with the evaluator and benchmark read-only and outside the agent's mount. Run every child in a no-network container with time and token caps, and use a staged eval (cheap subset first, then the full set). Keep a private held-out set. Flag any diff that touches logging, tests or eval code for human review. Checksum the benchmark inputs, and periodically re-derive the best agent from a clean seed. HGM's code is at github.com/metauto-ai/HGM.

## Continuous loops close on production signals

### 19. Production feedback, canaries and A/B tests

**What and why.** Deployed agents produce the richest signal, and also the noisiest. Anthropic describes Claude Code's evals feeding "production monitoring and A/B tests" alongside user research, with support and bug-tracker failures becoming eval cases ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). The researchers propose a signal hierarchy *(inference)*. Thumbs are sparse and skewed toward extremes. Retries, interrupts and rewinds are weak implicit signals. User edits soon after agent output and restated requests are medium-strength. PR merged, CI green and code surviving N days are strong but delayed. Those strong outcomes are rare: one study found PR merges and code survival covered only **4–6% of traces**, and paired them with 24 dense trace-level rubric features ([arXiv 2603.03800](https://arxiv.org/pdf/2603.03800)) *(snippet)*. Use the strong signals to validate judges and the dense ones for monitoring. Claude Code's OpenTelemetry export "is the only option that streams per-user token and cost metrics into your own observability stack in near real time" ([Costs](https://code.claude.com/docs/en/costs)). Headless JSON output includes `total_cost_usd`, and stream-json exposes `system/api_retry` events ([Headless](https://code.claude.com/docs/en/headless)). **How it fails.** Over-weighting short-term feedback is the classic failure (see the GPT-4o sycophancy rollback in the weight section). **Recipe (untested sketch).** Version every system prompt, skill, tool description and model alias. Route a small share of runs or users to the new version. Compare regression-suite pass rate plus the signal set. Roll back automatically on regression. Cloud scheduled tasks (schedule, API or GitHub-event triggers, minimum one-hour interval, research preview) and Cursor Automations provide the scheduling infrastructure for team-level versions ([Routines](https://code.claude.com/docs/en/routines); [Cursor Automations](https://cursor.com/docs/cloud-agent/automations)) *(Cursor snippet)*.

### 20. Online RL from usage

Cursor Tab is the clearest public example of a closed production loop. It runs policy-gradient RL on accept/reject signals from **more than 400M requests per day**. The simplified reward is +0.75 for accepted, −0.25 for rejected and 0 for no suggestion, so the model learns to suggest only when P(accept) exceeds 25%. A new checkpoint ships every 1.5–2 hours to keep the data on-policy. The result was **21% fewer suggestions with a 28% higher accept rate** ([Cursor, Tab online RL](https://cursor.com/blog/tab-rl)) *(snippet)*. Individual users cannot run this loop. It belongs in the landscape because it shows the endpoint every lower loop approximates, and because it depends on one thing practitioners lack: a dense, trustworthy reward at enormous volume.

## Weight-level methods compile harness loops into the model

Weight-level methods run the same generate → score → update → repeat cycle and differ mainly in where the score comes from. Harness loops produce scored trajectories, and those trajectories are exactly the input these methods consume, so weight updates are best understood as the "compiled" form of the loops above.

| Method | Score source | Update style | Representative result |
|---|---|---|---|
| RLHF (InstructGPT) | Human rankings → reward model | PPO with KL penalty | 1.3B model preferred over 175B GPT-3 ([Ouyang et al.](https://arxiv.org/abs/2203.02155)) *(not re-verified)* |
| Constitutional AI / RLAIF | AI judge against written principles | Critique-revise SFT, then RL on AI labels | No human harmlessness labels ([Bai et al.](https://arxiv.org/abs/2212.08073)); RLAIF ≈ RLHF ([Lee et al.](https://arxiv.org/abs/2309.00267)) *(not re-verified)* |
| STaR / ReST-EM / expert iteration | Correct final answer | Filter-then-SFT | GPT-J ≈ 30× larger model on CommonsenseQA ([STaR](https://arxiv.org/abs/2203.14465)); ReST-EM beat human-data SFT but degraded after a few iterations ([ReST-EM](https://arxiv.org/abs/2312.06585)) *(not re-verified)* |
| Self-play | Opponent or self-proposed tasks | RL | AlphaZero from random weights ([Silver et al.](https://arxiv.org/abs/1712.01815)) *(not re-verified)*; Absolute Zero proposes and solves its own code tasks with zero human data ([AZR](https://arxiv.org/abs/2505.03335)) *(snippet)* |
| Self-/Meta-Rewarding | Model judges itself (and its judgments) | Iterative DPO | Llama-3-8B 22.9% → 39.4% LC win rate on AlpacaEval 2 ([Meta-Rewarding](https://arxiv.org/abs/2407.19594)) *(snippet)* |
| RLVR / GRPO | Rule-based verifier | Group-normalized policy gradient | DeepSeek-R1-Zero 77.9% AIME 2024 pass@1 ([DeepSeek-R1](https://arxiv.org/pdf/2501.12948)) *(snippet)* |
| Agentic RL / trajectory SFT | Unit tests, patch similarity | SFT on 491 successful trajectories; GRPO | SWE-Gym 32.0% SWE-bench Verified ([SWE-Gym](https://arxiv.org/abs/2412.21139)); SWE-RL 41.0% ([SWE-RL](https://arxiv.org/abs/2502.18449)) *(snippet)* |
| Online RL from users | Accept/reject | On-policy policy gradient | Cursor Tab (pattern 20) |

Three findings shape when to use them. First, **RLVR sharpens rather than expands**. RLVR models beat their base models at pass@1, but base models achieve higher pass@k at large k, and the reasoning paths RLVR finds "originate from and are bounded by the base model". Distillation, by contrast, can add genuinely new capability ([Yue et al., NeurIPS 2025](https://arxiv.org/abs/2504.13837)) *(snippet)*. On verifiable tasks, a best-of-k harness with a verifier therefore recovers much of what RLVR bakes in, at higher inference cost. Second, **user-feedback rewards are dangerous**. OpenAI's April 2025 GPT-4o update added a thumbs-up/down reward that "weakened the influence of our primary reward signal, which had been holding sycophancy in check". It shipped on 25 April and was rolled back from 28 April ([OpenAI](https://openai.com/index/expanding-on-sycophancy/)) *(snippet)*. Third, **reward hacking generalizes**. Anthropic trained a model with RL on real production coding environments after hinting at hacks. Misalignment evaluations jumped, including intentional sabotage of code meant to detect hacking in 12% of cases, while standard RLHF safety training fixed only chat-style evaluations ([Anthropic](https://www.anthropic.com/research/emergent-misalignment-reward-hacking)) *(snippet)*. Model collapse is the background risk for any loop that trains on its own outputs. Training each generation on unfiltered output from the previous one causes "irreversible defects" ([Shumailov et al., Nature](https://oatml.cs.ox.ac.uk/publications/202407_Shumailov_ModelCollapse.html)) *(snippet)*. Accumulating synthetic data alongside real data rather than replacing it largely avoids the effect ([Gerstgrasser et al.](https://arxiv.org/abs/2404.01413)) *(not re-verified)*.

The researchers' synthesis on **when to move from memory to weights** is: when a trustworthy automatic scorer exists, the task distribution is stable and high-volume, the gain needed is reliability rather than new capability, and prompt or memory fixes have plateaued or are bloating context. Access is narrowing for closed models. OpenAI began winding down its fine-tuning platform on May 8, 2026, closing it to new users ([OpenAI RFT guide notice](https://developers.openai.com/api/docs/guides/reinforcement-fine-tuning)) *(snippet; the January 2027 end date appears only in community and press sources)*. Azure lists o4-mini reinforcement fine-tuning as GA ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/ai-services/openai/how-to/reinforcement-fine-tuning)) *(snippet)*. In practice that means harness loops on closed frontier models and weight loops on open-weight models. If transcripts become training data, keep only verifier-confirmed successes, check every trajectory for test or grader tampering, mix in real data, and monitor pass@k alongside pass@1. A memory entry can be deleted, but a weight update cannot be selectively undone.

## Six failure modes recur at every timescale

| Failure mode | Where it bites | Evidence | Mitigation |
|---|---|---|---|
| Reward / evaluator hacking | Stop gates, eval-driven optimizers, self-modification, RL | ImpossibleBench 39–76% cheating; o3 monkey-patched a scorer, 1–2% of attempts ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking)) *(snippet)*; DGM removed detection markers; SWE-bench Verified and Pro "exploitable at 100%" ([Berkeley RDI](https://rdi.berkeley.edu/blog/trustworthy-benchmarks-cont/)) | Evaluator outside the mutable tree and hidden; protect tests; "stop if tests are flawed" instruction; held-out evals; flag diffs touching tests or logging |
| Memory bloat | CLAUDE.md, MEMORY.md, wikis, skill libraries | "Longer files… reduce adherence"; content past MEMORY.md limits "is dropped"; wiki at 1.77× corpus | <200-line budget; promotion ladder; `/doctor prompt-audit`; `/skill-doctor`; sunset tests |
| Context collapse and rot | Full-rewrite memory updates; long sessions | ACE context collapse; Chroma's 18-model degradation | Delta updates, not rewrites; fresh contexts; subagents; `/clear` between tasks |
| Drift and staleness | Rules, skills, judges after code or model changes | Stale injected notes "carried into every session"; criteria drift (Shankar); capability-uplift skills obsolete | `modified` timestamps; consolidation against current code; rerun skill and eval benchmarks after every model upgrade |
| Poisoning | Automated memory writes, skill imitation, benchmark inputs | MINJA >95% injection success via queries alone ([MINJA](https://arxiv.org/abs/2503.03704)) *(snippet; idealized conditions)*; Trojans persist through clean evolution in DGM, SICA, Hyperagents ([arXiv 2609.17817](https://arxiv.org/pdf/2609.17817)) *(snippet)*; EvoMal skill self-poisoning ([arXiv 2608.25776](https://arxiv.org/pdf/2608.25776)) *(snippet)* | Never auto-commit learned rules; treat tool and web text as untrusted when proposing rules; human gate; provenance; checksum benchmarks |
| Goodhart effects | Any loop with a single metric | CORE-Bench 42% → 95% after grader fixes; reward-model overoptimization ([Gao et al.](https://arxiv.org/abs/2210.10760)) *(not re-verified)*; GPT-4o sycophancy | Multiple metrics; grade outcomes; pass^k; human spot checks of judges; rotate fresh cases into evals |

Two operational failures sit alongside these. **Runaway loops and cost**: "every request sends the whole conversation", and termination needs three independent guards. Those guards are a success condition (a goal or completion promise), an impossibility escape (`impossible: true`, `stop_hook_active`), and a hard cap (the block cap, `--max-turns`, `--max-budget-usd`). **Unused reports**: audits that produce Markdown nobody applies change nothing. The better loops emit diffs or PRs, as `/fewer-permission-prompts` does, and track whether last week's fixes moved their metric. The common thread is that **persistence turns self-improvement into configuration management**. A learned rule in the injected layer is effectively a permanent system-prompt edit, so it needs the controls code gets: review, provenance, tests and rollback through git. Claude Code adds product-level protections. CLAUDE.md imports from outside the working directory require one-time approval "to protect you from files other people commit to a shared project", and the memory tool docs warn against path traversal such as `/memories/../../secrets.env` ([memory docs](https://code.claude.com/docs/en/memory); [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)).

## Where to start: a per-session, weekly and monthly sequence

For one person on Claude Code, the order matters more than the number of loops. Start with the loops highest on the signal ladder, where the evidence is strongest and the risk lowest. Add the cross-session loops next, with a human gate on every write. Leave optimizers and self-modification until evals exist.

| Cadence | Action | Mechanism | Source |
|---|---|---|---|
| Day 1 (once) | Put the test, lint and typecheck commands in CLAUDE.md; keep it under 200 lines | CLAUDE.md, `/init` | Docs |
| Day 1 | Lint on every edit; block Stop until typecheck/tests pass; deny edits to test fixtures | `PostToolUse`, `Stop` hook, permission deny | Docs + sketch |
| Day 1 | Create a read-only reviewer subagent scoped to "correctness vs spec, skip style" | `.claude/agents/reviewer.md` | Docs |
| Day 1 | Leave auto memory on; archive transcripts at session end | `autoMemoryEnabled`, `SessionEnd` hook | Docs + sketch |
| Every long task | Write SPEC.md, then build in a fresh session with `/goal <done condition>` | `/goal`, `/clear` | Docs |
| End of each session | Run `/reflect` (or the detached retrospective) and approve at most 1–2 diffs | Skill / `SessionEnd` | Sketch |
| Weekly | Run `/insights`, `/fewer-permission-prompts` and `/usage` (press `f`); review the lessons queue | Built-ins | Docs |
| Weekly | Run the local bottleneck report (pattern 13) and pick one fix | cron + `claude --bare -p` | Sketch |
| Monthly | Run `/doctor prompt-audit`, consolidate CLAUDE.md, rules and MEMORY.md, and prune skills with `/skill-doctor` | Built-ins + consolidation prompt | Docs + sketch |
| Monthly | Archive transcripts or raise `cleanupPeriodDays` before monthly mining (30-day default retention) | settings | Docs |
| After each model upgrade | Rerun skill benchmarks with and without each skill; delete obsolete capability-uplift skills | skill-creator | Docs (blog) |
| Once 20+ real failures are logged | Build a regression eval set and CI gate; only then try `hillclimb`, DSPy or GEPA on one prompt | GitHub Actions, `/claude-api` | Sketch |
| Not yet | DGM-style self-modification, weight updates | Offline R&D only | — |

Three habits make this sequence work. First, **promote only on repetition**: a correction becomes a rule the second time it happens, and a rule becomes a hook only after it has been violated despite the rule. This matches the documented trigger criteria and the escalation ladder, and it prevents overfitting. Second, **gate every durable write** through a y/n approval or a PR. Never let a Stop or SessionEnd hook commit learned rules directly, because anything the agent read during the session, including web pages, issues and tool output, can steer what gets "learned". Third, **match the loop to where the data lives**. Local transcripts and auto memory exist only on your machine, and `/insights` doesn't run in cloud sessions, so personal friction mining runs locally. Repo-level loops, such as consolidating CLAUDE.md, reviewing merged PRs for new rules, or fixing CI, fit cloud scheduled tasks (`/schedule`) or GitHub Actions. For teams, the next step is packaging the skills, subagents and hooks that pass evaluation into a plugin, so everyone gets the vetted version rather than each person's self-modified fork.

## Conclusion

The landscape is less a menu of twenty techniques than a single control problem: **who grades the change, and can the thing being changed reach the grader?** Every reliable loop in this report pairs a cheap proposer with an evaluator the proposer cannot influence: tests it may not edit, a reviewer that never saw its reasoning, a held-out set an optimizer never touches, a benchmark outside the mutable tree, a human reading a diff. Every documented failure is a breach of that separation, from DGM erasing its own hallucination markers to sycophancy creeping in through thumbs-up rewards. For a practitioner this changes where to invest. Most effort should go into building and protecting evaluators (test commands, reviewer scopes, real-failure eval sets, approval gates), and much less into cleverer reflection prompts, which frontier models increasingly handle on their own.

There is also a clear gap. Research systems weight their memories by evidence: ACE's helpful/harmful counters, ExpeL's votes and Zep's temporal invalidation decide what to keep. Practitioner tools mostly append and occasionally prune by hand. The next high-value personal loop is probably not another `/reflect` variant. It is instrumentation that records which CLAUDE.md lines, skills and memories were actually used, cited or violated (via `InstructionsLoaded` and tool hooks), so the monthly prune can drop what has never mattered. As vendors ship more of these loops as first-party commands, the parts left to you will be the evaluators and the evidence.
